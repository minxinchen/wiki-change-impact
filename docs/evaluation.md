# 研究：來源圖比直接搜尋多解決什麼？

Author: Nio (Master) · Implementation: Codex · 2026-10-10

## 背景與目標

之前的 demo 證明來源切換能傳播到三頁，卻沒有比較簡單做法，也没有揭露資料宣告不完整時的結果。本輪目標是以可檢查輸入，回答「工具能否列出需要重新核對的頁面，以及多列／漏列的代價」。不以程式測試通過替代方法效益。

## 相關實作與取捨

[pytest-testmon 的固定版本測試](https://github.com/tarpas/pytest-testmon/blob/dccc58d2ed8edec98096ff1974acb7c07d3e3482/tests/test_process_code.py)驗證執行覆蓋與內容指紋如何影響重跑選擇。本工具則依賴作者宣告的 sources，沒有程式執行覆蓋可以觀察，因此不能借用它的依賴完整性假設。借鏡的是把變更類型、選中與未選中的對象做成可重跑案例；未執行外部 benchmark，也不宣稱本工具與其等效。

## 材料與方法

完整材料：[cases.json](../evaluation/cases.json)。四份 Wiki 正文、一組虛構政策與保留期限來源，形成三層依賴及一份無關頁面。九種情境包括不變、事實更正、格式變動、換源、缺檔、正文依賴漏宣告、跨 vault、跨版接線與無關材料。

### 預期集合如何建立

Codex 在評估 runner 寫成前，依各案例的正文與變更語意編寫 `expected_review_pages` 及理由；不是用工具輸出回填答案。規則是「目前頁面的事實或支撐來源因該變更需要重新考慮」。純空白不改變事實；來源缺失雖未證明正文錯誤，仍需核對證據。

這仍是作者設計的開發集：不是人類 gold standard、盲測或獨立泛化資料。ChatGPT 複審會獨立檢查文字與標籤，但 agent 複審也不能改稱人類標註。`expected_status` 單獨描述位元組／依賴契約：漏寫 sources 的案例可能正確回 `unchanged`，同時漏掉正文上確實應核對的三頁。兩個判準不能混用。

### 三種方法

1. **直接文字搜尋**：已知案例的檔案變動清單，單次搜尋前後 Wiki 文字中的來源路徑，也列出被直接改動的 Wiki 頁；不遞迴追蹤。這是可重跑的 literal-scan 基準，不是聲稱已測量人類使用 rg 的表現。
2. **全部核對**：把範圍內四頁全部列出，作為保守負擔上界；沒有模擬人類判讀耗時。
3. **依賴工具**：使用正式 snapshot／compare，僅從追蹤檔案與宣告依賴產生結果。直接搜尋知道完整案例檔案 delta，工具只知道其追蹤集合；漏宣告案例正是這個部署邊界，不隱藏這個輸入差異。

runner 使用 temporary directory，結束後清除。結果保留前後檔案指紋、依賴與覆蓋、各方法實際列出／多列／漏列、理由與案例／程式指紋。暫存根目錄相關的 config／snapshot 識別不放入可攜評估結果；一般 CLI 的完整報告仍保留它們。

```sh
.venv/bin/python -B evaluation/run.py --out runs/evaluation-v2
```

## 結果

實際逐例結果：[results.json](../evaluation/results.json)。各案例分別計算集合交集、差集；相同頁面在不同變更案例中分開計數。九例共 18 個預期應核對的「案例－頁面」配對。

| 方法 | 正確列出 | 多列 | 漏列 | 總列出 |
|---|---:|---:|---:|---:|
| 直接文字搜尋 | 9 | 2 | 9 | 11 |
| 全部核對 | 18 | 18 | 0 | 36 |
| 依賴工具 | 15 | 3 | 3 | 18 |

最有意義的觀察是失敗分布：

- 正常來源更正中，工具找到三層正文；直接搜尋只找到直接提到來源的頁面。
- 格式變動中，工具多列三頁。這是以檔案 hash 保守追蹤的成本，不能把它算成三個成功案例。
- 正文仍依據政策、sources 卻錯填保留期限時，工具回 unchanged 且漏列三頁。直接文字搜尋反而能抓到一頁；依賴工具不是所有搜尋的替代品。
- 來源缺失回 blocked，即使仍提供候選頁面，也不能視為通過。
- 跨版本情境保留保守候選，但路徑每條邊標版本；共同版本為空時明示不是單版成立的鏈。

## 討論

這份小型開發集支持的結論是：完整宣告依賴時，遞迴分析可以補足單層查找；其代價與限制是格式變動的多列及漏宣告的漏列。計數不表示一般準確率、節省一半工時或生產可用性。

另外，聯集 BFS 每個來源到每頁只保留一條最短候選路徑。即使該條是跨版拼接，也不能推論不存在另一條單版有效路徑；`path_scope` 只描述這次輸出的路徑。保留聯集是避免刪除關係時過早排除影響的取捨。

## 結論與停止條件

本輪把問題收斂為「可解釋的來源變更候選清單」。W1 覆蓋缺口和 W2 路徑版本需通過反例測試；W3 補足公開可重跑資料、簡單方法對照與失敗揭露。尚未完成的是獨立真實語料上的效益驗證，不應標成已證明業務成效。

不加入 embedding、語意自動修文或核准工作流。下一輪是否擴充，應由新增實際案例的漏列／多列型態決定。
