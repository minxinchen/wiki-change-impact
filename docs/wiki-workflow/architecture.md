# Wiki 工作流：五項功能與責任

Author: Nio (Master) · Reconstruction: Codex · 2026-10-10

## 設計依據

[Karpathy 的原始 pattern](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)將原始材料、持續整合的 Wiki 與操作規約分開，涵蓋 ingest、query、lint 與有價值答案的寫回。本案借用這個組織原則，不把其對維護成本的描述當成本系統實測結果。

本 repo 的 RAG 指「取得外部知識供生成使用」的工作流；Wiki 另外承擔查詢前的知識整合。此命名不表示原 pattern 自稱傳統 chunk-based RAG，也不表示 embedding 無效。

## 功能與目前實作

| 功能 | 既有材料中的做法 | 需要驗收的問題 |
|---|---|---|
| 整理 | raw 保留；機型、概念、證據、主題分頁；Ingest SOP | 新來源是否整合既有頁，是否誤刪限定條件 |
| 關聯 | index、related_concepts、系列關係、evidence ID、sources | 相關性與證據支撐是否混用；連結是否幫助取用 |
| 檢索 | index-first、依問題讀頁、必要時回查 raw | 入口是否衝突；是否取得有效知識而非舊卡 |
| 追溯 | sources、原始校正紀錄、facts、log | 每項回答主張能否回到支撐段落；來源是否真的支持 |
| 更新 | 人類校正、Agent 修訂多頁、更新 index/log 的 SOP | 內容、來源、入口是否一起更新；重問後能否維持修正 |

## 邊界設計

- 原始材料保留原樣；整理頁允許修訂，修訂需記來源與原因。
- 同一知識的有效版本由明確入口與狀態指定，不由「哪個檔案較新」自行推斷。
- 更新從既有節點開始判斷，避免同一概念另建平行 Wiki；需要新節點時說明關係與理由。
- `sources` 表示依據；`related` 表示導覽關係，不能互相替代。
- Agent 負責整合與回答，reviewer 查主張和來源；遇領域分歧由來源或使用者釐清，不能用多 agent 一致同意代替事實。
- 統一入口是邏輯責任，不要求搬移正式 vault。本輪未調整正式 memory、wiki 或 auto-load。

## 現有工具的位置

[Change Impact](../change-impact-tool.md)回答「哪些已宣告依賴的頁面可能需要重查」。它不負責從材料產生知識、不建立語意關係、不挑選有效入口、不生成答案，也不驗證引用是否支持主張。

因此它保留為更新輔助；對整套系統的驗收必須包含讀取與生成、整合與重問。目前新增了受限模型檢索、隔離更新與本案維護檢查的實驗執行器；語意驗收未通過，尚未串成可供日常使用的完整服務。不能把流程圖當成已完成的產品 API。
